# Design: Self-Contained Questions Restructure

## Context

The repo is a single Go module (`github.com/jones/interesting-interview-questions`)
whose `questions/` tree holds 40 library packages, each a stub + hand-written
test. Stubs are generated by `cmd/generate` from `questions.yaml`; the problem
text lives in each `.go` doc comment. Tests import `internal/testutil` and
`internal/types`; the special kinds (`lru-cache`, `codec-tree`,
`max-path-tree`, `tree`, `list`) import `internal/types` from stubs too.
`bin/sync` protects the "no solutions in `.go` files" rule via dirty-stub
detection, then runs `go build ./...` + `go test ./...` on the root module.

The repo is about to become multi-language (Python is the next change).
Each question must become a **self-contained, runnable program** so users
can clone, open one folder, and never touch repo-internal machinery.

## Goals / Non-Goals

**Goals:**

- Every Go problem is a standalone Go module: `go run .` compiles and exits
  0; `go test .` runs real tests against the stub.
- The problem statement appears exactly once per problem (generated
  `README.md`), never duplicated in code files.
- `questions.yaml` remains the single source of truth; `cmd/generate` is
  the only writer of stubs/READMEs.
- `bin/sync` enforces the committed-state invariant: stubs pristine, every
  problem builds, every problem's tests fail.
- Structure the generator so a Python emitter can slot in next change.

**Non-Goals:**

- No Python support (follow-up change, gated on this one).
- No changes to the `questions.yaml` schema.
- No test-case data in `questions.yaml` (tests stay hand-written).
- No external dependencies for problems (stdlib only).
- No `go.work` file (each module is built standalone; root tooling is
  unaffected — nested modules are auto-skipped by root builds).

## Decisions

### 1. Directory layout

```
questions/<difficulty>/<short-name>/
├── README.md              ← generated: "# Title" + URL link + question_text
└── go/                    ← self-contained Go program
    ├── go.mod             ← "module <sanitized-short-name>" (e.g. module twosum)
    ├── <short-name>.go    ← package main stub (two-sum.go)
    └── <short-name>_test.go ← package main, hand-written, real tests
```

Keeps the current file naming (`two-sum.go`, `two-sum_test.go`) and adds
the `go/` level that future `python/` sits beside. `short_name` is already
unique, so module names (sanitized: hyphens stripped) cannot collide.

### 2. Stub shape (package main)

```go
// two-sum.go — generated
package main

// TwoSum solves Two Sum. See README.md for the problem statement.
func TwoSum(nums []int, target int) []int {
	return nil
}

func main() {}
```

- **Exported functions** (same names as today) — keeps the yaml `signature`
  semantics and reads naturally.
- **Trivial `func main() {}`** — makes the program runnable (`go run .`
  exits 0) without pretending to be a CLI.
- **Doc comment is one line** pointing at `README.md` — satisfies the
  no-duplication rule.
- **Inlined `TreeNode`/`ListNode`** definitions for `tree`/`list` kinds and
  the `lru-cache`/`codec-tree`/`max-path-tree` special cases — drops the
  `internal/types` import.
- **`go.mod`** with `module <sanitized>` and the same `go` version as the
  root module.

### 3. Test files

Tests stay **hand-written, proper tests** (real cases that validate a
user's filled-out solution), rewritten once to be self-contained:

- `package <pkg>_test` → `package main` (same folder, no import needed)
- `twosum.X(...)` → `X(...)` (strip package qualifiers)
- `types.TreeNode` → `TreeNode`, `types.ListNode` → `ListNode`
- `testutil.AssertEqual*` → stdlib equivalents (only `two-sum` uses it)
- drop all `internal/*` imports

The transform is mechanical and covered by the migration tool (see below).
`cmd/fix_tests` was the opposite transform (adding qualifiers/imports) —
its purpose disappears, so it is deleted.

### 4. `cmd/generate` becomes a repo-wide generator

Generation logic moves from flat functions in `cmd/generate/main.go` into
an `internal/generate/` package with an emitter-oriented shape, so the
Python emitter (change 2) drops in without restructuring:

- `internal/generate/generate.go` — load yaml, iterate specs, delegate per
  language
- `internal/generate/readme.go` — render `README.md` from `question_text`
  (`# <Title>` + URL link + statement)
- `internal/generate/go.go` — render `go.mod` + `package main` stub
  (signature-based and kind-based templates, inlined types)

`internal/question` (yaml loader) is retained as-is.

### 5. `bin/sync` reworked verification

```
Phase 1  regenerate (temp) → diff vs committed stubs + READMEs
         dirty? → restore, abort (unless FORCE=1, which overwrites)
Phase 2  root module: go build ./...   (cmd/ + internal/ tooling)
Phase 3  per problem (questions/*/*/go/):
         go build ./...   → MUST succeed
         go test ./...    → MUST fail (non-zero exit)
```

The failing-test check works because tests assert real values and stubs
return zero values — at least one case always fails. Phase 3 doubles as
the migration validator: every moved problem must build and fail.

### 6. Migration of the 40 existing questions

A temporary `cmd/migrate` tool performs the one-off transform (layout
move + test rewriting + go.mod creation), then is **deleted** before the
change completes — the permanent workflow is "generator writes stubs,
you hand-write tests", so no migration tooling survives.

### 7. Dead code removal

`internal/types`, `internal/testutil`, and `cmd/fix_tests` are deleted
once nothing references them. `cmd/report` keeps reading `questions.yaml`
(unchanged behavior; path references, if any, adjusted).

### 8. Docs and commands

Root `README.md` user flow changes from "go test ./..." to "pick a
problem, read README.md, implement in `go/`, `go test .` there". A new
`bin/test` helper walks every language folder and runs its tests (the
replacement for root-level `go test ./...` which no longer reaches
nested modules). `AGENTS.md` command table is updated accordingly.

## Risks / Trade-offs

- **Test migration churn (40 hand-written files)** → the transform is
  strictly simplifying (strip qualifiers/imports); `cmd/migrate` + per-problem
  `go build`/`go test` validation catches every break; rollback is `git reset`.
- **Inlined `TreeNode`/`ListNode` drift** (7 problems now duplicate type
  definitions) → accepted cost of self-containment; types are 5 lines and
  stable; yaml still records signature/kind so the generator owns them.
- **Failing-test invariant false positive** (a stub passing all cases) →
  effectively impossible with real table tests; sync fails loudly if
  `go test` exits 0, which only happens if the stub got implemented.
- **Nested modules confuse naive `go test ./...`** → documented; `bin/test`
  is the canonical "run everything" entry point; editors can still open
  each module directly.
- **Two `go.mod` files must agree on Go version** → generator emits the
  version from the root module's `go.mod`, single source.
- **`main()` could encourage CLI experiments** → deliberate trade-off for
  "runnable program"; `go test` remains the real interface.

## Migration Plan

1. Rework generator (`internal/generate/` + `cmd/generate`) with new stub
   and README output; add `go.mod` emission.
2. Rework `bin/sync` (dirty detection incl. README, per-problem
   build + fail-test verification).
3. Build `cmd/migrate`: for each of the 40 problems, move files into
   `go/`, generate README + go.mod, rewrite the test file in place.
4. Run migration; run `bin/sync`; fix fallout problem-by-problem.
5. Delete `cmd/migrate`, `cmd/fix_tests`, `internal/types`,
   `internal/testutil`; grep to confirm zero references.
6. Update `README.md`, `AGENTS.md`, add `bin/test`.
7. Final gate: `./bin/sync` green, `go run ./cmd/report/` works.
